# VEAI アカウント(共通認証)アーキテクチャ

2026-07-19 オーナー決定。veai.jp 配下のコンシューマ向けアプリの認証は、Care Quest の Cognito User Pool を共用する単一の「VEAI アカウント」に統一する。

## なぜ1アカウントにするのか

パスワードマネージャー(Bitwarden 等)はベースドメインで資格情報を照合するため、veai.jp 配下でアプリごとに別アカウントを作ると、ユーザーの保存済みパスワードが veai.jp に乱立して混乱する。ユーザーから見て「veai.jp のアカウントは1つ」にするのが目的。サブドメイン分割は Bitwarden の既定照合を解決せず、S3/CloudFront のパス配信構成も壊すため不採用。

## ローカルファースト原則との関係(変更なし)

- アカウントは**すべてのアプリで任意**。サインインなしで全機能が使えるローカルファースト設計は、この方針の前提であり変わらない
- かんたん家族サポートのようなアカウントレスのツールは、今後もアカウントを持たない

## 構成

- **User Pool**: `CareQuestUserPool`(このリポジトリの CDK スタックが所有)。`VeaiSharedUserPoolId` として CloudFormation エクスポート済み
- **アプリクライアント**: アプリごとに専用の `UserPoolClient` を作る(Care Quest 用は既存の `CareQuestUserPoolClient`)。トークンはアプリ単位で発行される
- **データ**: アプリごとに独立した DynamoDB テーブル。アカウント(sub)はパーティションキーの一部にすぎず、テーブルをまたぐ読み書きは作らない
- **API**: アプリごとの API Gateway + オーソライザー。他アプリのトークンスコープを受け入れない

## ブレーキ設計(登録≠全サービス利用)

新しいアプリが VEAI アカウントを使うときの必須要件:

1. **初回サインイン時の明示同意** — 「◯◯で VEAI アカウントを使いますか?」の確認画面を必ず挟む。同意して初めてそのアプリの enrollment(初回レコード)が作られる
2. **同意までデータゼロ** — アカウントが存在しても、そのアプリでサインイン+同意するまで、そのアプリのテーブルにレコードを一切作らない
3. **プライバシーポリシーへの明記** — (a)アカウントは veai.jp 共通 (b)データはサービスごとに独立 (c)同意までデータは作られない、の3点を各アプリのプライバシーページに書く(Care Quest の app/privacy/page.tsx が雛形)

## 対象と対象外

- **対象**: コンシューマ向けアプリ(Care Quest、CareReady、おくすりの約束、GutPacer、ParkinSync 等)
- **対象外**: 施設・事業所向けアカウント(B2B)。組織管理・スタッフ権限・監査ログが必要になるため、個人の VEAI アカウントとは**別の User Pool** として設計する(個人の介護記録と職務アカウントを同じ鍵にしない)。施設スタッフが個人として家族向けアプリを使う場合は、通常の VEAI アカウントを別途作る

## 将来

- パスキー(WebAuthn)対応でパスワード自体を減らす。共通 Pool にしておけばパスキーも1つで済む
- ユーザー向け表記は常に「VEAI アカウント」。Cognito などの実装名は UI に出さない
