# Care Quest 戦略ドキュメント

Last updated: 2026-07-07 JST

このドキュメントは Care Quest の (1) 開発に使うスキルセット、(2) 開発戦略、(3) マーケティング戦略、(4) 詳細ユーザーストーリー、(5) 開発費用見積もり をまとめたものです。`docs/project-skills.md`(技術スキルの詳細)と `docs/project-management.md`(タスク管理)を補完する上位の戦略文書として使います。

## 1. Fable(Claude Code)が開発に使うスキル

AI エージェント(Fable / Claude Code)が本プロジェクトを開発する場合に実際に使うスキルを、「エージェント運用スキル」と「技術スキル」に分けて整理します。

### 1.1 エージェント運用スキル(Claude Code の機能)

| スキル / 機能 | 使いどころ |
| --- | --- |
| `/code-review` | PR 前の差分レビュー。正確性バグと簡素化の指摘。development → main マージ前に必須にする |
| `/verify` | 修正が実際に動くかをアプリを起動して確認。特にログイン・記録フローの回帰確認 |
| `/security-review` | Cognito・API Gateway・IAM 周りを触った PR の前に実行。実ユーザーデータ投入前に一度フル実行 |
| `/simplify` | MVP で急いで書いたコードの整理。lib/storage.ts の AWS 同期対応時に有効 |
| Explore / Plan エージェント | 大きめの機能(同期戦略、通知など)の実装前調査と設計 |
| GitHub Issues 連携 (`gh`) | `docs/project-management.md` のワークフローに沿った Issue 起票・更新 |
| メモリ | 「CloudFront の cache behavior 上限に達している」等、コードから読み取れない運用上の制約の記憶 |

### 1.2 技術スキル

詳細は `docs/project-skills.md` のスキルマップを参照。要点のみ:

- **Next.js 16 App Router + 静的エクスポート**: `basePath: /carequest`、`output: "export"`。**必ず `node_modules/next/dist/docs/` を読んでから書く**(AGENTS.md ルール)
- **React 19 / TypeScript / Tailwind CSS 4**: UI とクライアント状態管理
- **AWS CDK**: Cognito・API Gateway・Lambda・DynamoDB(`infra/`)
- **CloudFront + S3 運用**: `veai-jp-toc-web/carequest/` 配信、invalidation は `/carequest/*`
- **GitHub Actions**: CI とデプロイの検証

### 1.3 プロダクト固有のスキル(最重要)

技術より大切な、このプロダクト特有の判断基準:

- **介護者の心理的負荷への配慮**: 競争させない、責めない、比較させないトーン。ゲーミフィケーションは「達成」ではなく「意味づけ」のために使う
- **ローカルファースト**: サインインしなくても今日の記録ができること。AWS 同期は enhancement であり blocker にしない
- **安全性への配慮**: 医療アドバイスをしない。危機的状況(介護うつ等)への適切な誘導(相談窓口リンク)を About に維持する

## 2. 開発戦略

### 2.0 プロダクトビジョン(オーナー・2026-07-13)

- **「あなたは孤独ではない」を静かに示すことが中核価値。** 介護は重く、会話すれば苦労話になりがちで、話したくない人も多い。だから会話・交流を強いず、「他の誰かも今日、介護に向き合っている」**気配**だけが伝わる設計にする(第一弾: 今日のともしび)
- **エコシステム構想**: 今後、在宅介護に役立つアプリを複数リリースしていく。Care Quest はその**中心的なコミュニティ機能**を担う(共通アカウント=Cognito を将来のアプリ群で共有する布石)
- **介護者は恒久無料・広告なし**(§3.2 Phase 3 の収益方針と一体)

### 2.1 基本方針

- **小さく出して、実ユーザーの声で決める**。MVP は既に `veai.jp/carequest/` で公開できる状態。機能追加より「使い続けてもらえるか」の検証を優先する
- **1人 + AI エージェント体制を前提にする**。人間はプロダクト判断・実機確認・AWS 秘匿情報の管理、AI は実装・レビュー・ドキュメントを担う
- **ランニングコストをほぼゼロに保つ**(サーバーレス + 静的配信)。ユーザーが増えるまで固定費を作らない

### 2.2 フェーズ計画

#### Phase 0: リリース準備(〜2週間)— 現在地

- [ ] GitHub Actions 本番シークレットの確認(P1、既存 Issue)
- [ ] 実メール Cognito サインアップのスモークテスト(P1)
- [ ] development → main マージのリリース判断(P1)
- [ ] ローカルファースト保存の実装確定(P2)
- [ ] AWS インフラの本番前ハードニング: RemovalPolicy、CORS、ログ保持(P2)

**Exit 条件**: 本番 URL で「記録 → リロード → 残っている」が誰でも再現できる。

#### Phase 1: 定着検証(1〜2ヶ月)

目標: **10〜30人の実介護者に2週間以上使ってもらい、継続率と定性フィードバックを得る**。

- 記録の AWS 同期(サインイン時のみ、ローカルとマージ)
- ふりかえりの履歴表示(過去7日分)
- PWA 化(ホーム画面追加、オフライン動作)— 介護現場はスマホ利用が主
- 簡易アンケートフォーム(Google Forms 埋め込みで十分)
- 計測: CloudFront ログ or 軽量な自前イベント計測(Lambda 1本)。GA 等の重い計測はまだ入れない

**Exit 条件**: 週次継続率と「また使いたいか」の定性データが揃い、Phase 2 の優先順位を実データで決められる。

#### Phase 2: 価値の深化(3〜6ヶ月)

Phase 1 のデータ次第で以下から選択(全部やらない):

- **励ましメッセージの Bedrock 連携**: テンプレートから、記録内容とエネルギーレベルに応じた生成メッセージへ。コスト上限を設けたうえで導入
- **週間ふりかえりレポート**: 「今週あなたがしたこと」を優しく要約。メール or アプリ内
- **家族内共有**: 同じ被介護者をケアする家族間で記録を共有(要 Cognito グループ設計)
- **コミュニティ画面の実データ化**: 現在モックの「みんな」画面を実データに。ただし比較・競争にならない見せ方を厳守

#### Phase 3: 持続可能性(6ヶ月〜)

- 収益化の検証(後述のマーケティング戦略参照)
- 自治体・地域包括支援センター・介護事業者との連携検討
- アクセシビリティ監査(高齢の介護者も多い)

### 2.3 開発運用ルール

- ブランチ: `development` に集約 → 確認後 `main`(本番)
- 全 PR: lint + test + build + CDK synth の CI green を必須（E2E は PR 時に自動実行）
- タスク管理: GitHub Issues + Projects(`docs/project-management.md` 準拠)
- AWS 変更: `npm run aws:status` → 変更 → `npm run smoke:backend` / `smoke:prod`
- **CloudFront の制約**: Free プランの cache behavior 上限に達しているため、`/carequest/*` 専用 behavior は追加しない

## 3. マーケティング戦略

### 3.1 ターゲットとポジショニング

**一次ターゲット**: 在宅で親・配偶者を介護する 40〜60代の家族介護者(日本国内約700万人規模)。特に「介護記録アプリは事務的すぎて続かない」「頑張りを誰にも認めてもらえない」と感じている層。

**ポジショニング**: 「介護の管理ツール」ではなく **「今日できたことに意味を見つける、介護者自身のためのアプリ」**。競合(ケアズ・コネクト等の事業者向け記録システム、家族向け見守りアプリ)が「被介護者の管理」を軸にするのに対し、Care Quest は「介護者のセルフケア」を軸にする。ここが唯一の差別化ポイントなので、機能追加でこの軸をぶらさないこと。

### 3.2 フェーズ別施策

#### Phase 1(定着検証期): 手売りで10〜30人

コストゼロ、足で稼ぐ期間。

- 知人・家族経由で実介護者に直接依頼(最も質の高いフィードバック源)
- 介護者向けオンラインコミュニティ(X の介護垢界隈、介護系 Discord、ケアラーズカフェ)での紹介。**宣伝ではなく「作った理由」を語る**。介護コミュニティは商業的な売り込みに敏感
- note / ブログで開発の背景ストーリーを1本書く(「なぜ介護を"クエスト"にしたのか」)

#### Phase 2(拡大準備期): コンテンツと検索

- **SEO**: 「介護 記録 アプリ 無料」「介護 疲れた 自分を褒める」等のロングテール。veai.jp ドメイン配下なのでブログ/LP を同ドメインに置く
- **介護者支援団体との接点**: 一般社団法人ケアラーアクションネットワーク等、家族介護者支援 NPO に紹介を打診。営利色が薄い今の形は提携しやすい
- **地域包括支援センター向けチラシ**(A4 1枚 + QR)。ケアマネジャーが家族に渡せる形

#### Phase 3(持続化期): 収益モデルの検証

**オーナー決定(2026-07-13): ユーザー(介護者)からはお金を取らない。** アプリは介護者に対して恒久無料。収益はユーザー以外から得る。旧案のフリーミアム(ユーザー課金)はこの決定により撤回。

収益の3本柱(優先順):

1. **B2B2C(本命)**: 自治体・地域包括支援センター・介護事業者が「家族介護者支援メニュー」として導入(1団体あたり月額)。ケアマネが家族に渡せるツールは現場ニーズがあり、広告なし・非営利的な現在の形はむしろ営業上の強み
2. **助成金・補助金**: 介護テック/ヘルスケア系(経産省・自治体のスタートアップ支援)。**営利化前でも申請可能なものがあり、時期的に最初に動けるお金**
3. **スポンサー/CSR**: 介護関連企業・財団の協賛。「ユーザーに広告を見せる」のではなく「About に支援者として記載」程度の座組に留める

**やらないこと**: 介護者への広告掲載(疲弊した介護者に広告を見せるのはプロダクトの信頼を毀損する)、データ販売、**無料→後から有料化への転換**(信頼で成り立つアプリのため)。

### 3.3 計測する指標

| フェーズ | 北極星指標 | 補助指標 |
| --- | --- | --- |
| Phase 1 | 週次継続率(W1→W2 リテンション) | 1日あたり記録数、ふりかえり記入率 |
| Phase 2 | MAU、オーガニック流入数 | サインアップ完了率、PWA インストール数 |
| Phase 3 | 導入団体数(B2B2C)+ 獲得助成金額 | 団体の継続率、NPS ※ユーザー課金はしない(2026-07-13 決定) |

## 4. ユーザーストーリー(詳細検討パート)

### 4.1 ペルソナ

**ペルソナ A: 佐藤陽子(56歳・パート勤務)**
同居する83歳の母(要介護2、認知症初期)を介護して3年目。スマホは LINE と検索が中心。介護記録アプリを2つ試したが「入力項目が多くて事務仕事みたいで」1週間で挫折。夜、母が寝たあとに「今日も怒ってしまった」と自分を責めることが多い。

**ペルソナ B: 田中健一(43歳・フルタイム会社員)**
遠方の父(要介護1)を月2回訪問+日常は電話。介護「している感」が薄く、罪悪感がある。ITリテラシーは高い。妹と分担しているが、お互い何をしたか共有できていない。

**ペルソナ C: 山本美咲(35歳・ケアマネジャー)** ※Phase 3 の間接ユーザー
担当家族の疲弊に気づいても、かけられる言葉に限界がある。家族に渡せる「自分を労わるためのツール」を探している。

### 4.3 ユーザーストーリー詳細

書式: `US-番号 | 優先度 | フェーズ | ストーリー | 受け入れ条件 | 見積り`

#### EPIC-1: 記録する

**US-101 | P0 | Phase 0 | 実装済み・要検証**
佐藤さんとして、**アプリを開いてから10秒以内に今日したケアをタップで記録したい**。疲れていて文字入力する気力がないからだ。
- 受け入れ条件:
  - ホームから1タップでクエスト画面に到達できる
  - タスクはタップのみで記録され、確認ダイアログを挟まない
  - 記録直後に肯定的なフィードバック(ポイント + メッセージ)が表示される
- 見積り: 実装済み。実機での10秒検証のみ(30m)

**US-102 | P0 | Phase 0 | 実装済み・要検証**
佐藤さんとして、**アカウント登録せずに使い始めたい**。試す前に個人情報を求められると閉じてしまうからだ。
- 受け入れ条件:
  - サインインなしで記録・ふりかえりが完結する(localStorage)
  - サインインを促す表示は控えめで、機能をブロックしない
- 見積り: 実装済み。ローカルファースト方針の最終確認(既存 P2 Issue)

**US-103 | P1 | Phase 1**
田中さんとして、**スマホを替えたり別端末で見ても記録が残っていてほしい**。せっかくの記録が消えるのが不安だからだ。
- 受け入れ条件:
  - サインイン時、ローカル記録が AWS に同期される(ローカル → クラウドのマージ、重複なし)
  - 同期失敗時はローカルに残り、ユーザーには穏やかなエラー表示(赤い警告にしない)
  - サインアウト状態の挙動が明確(ローカルのみ、と表示)
- 見積り: 2〜3日(既存 P2 Issue「storage sync」に対応)

**US-104 | P2 | Phase 1**
佐藤さんとして、**リストにないケア(例: 夜中に3回起きた)も自由に記録したい**。私の介護は定型タスクに収まらないからだ。
- 受け入れ条件:
  - フリーテキスト or カスタムタスクの追加ができる
  - カスタムタスクにもポイントとやさしい説明文がつく(デフォルト文言でよい)
- 見積り: 1〜2日

#### EPIC-2: 意味を見つける

**US-201 | P0 | Phase 0 | 実装済み**
佐藤さんとして、**記録したときに「頑張りが認められた」と感じたい**。誰にも褒められない日々だからだ。
- 受け入れ条件: タスクごとに意味づけの一文が表示される(実装済み: `lib/tasks.ts` description)

**US-202 | P1 | Phase 1**
佐藤さんとして、**過去1週間の自分の記録をふりかえりたい**。「何もできていない」と感じる夜に、実際はやれていたと確認したいからだ。
- 受け入れ条件:
  - ふりかえり画面に過去7日分の記録サマリーが表示される
  - 記録が少ない日を責める表現を一切使わない(「0件」ではなく表示しない等の工夫)
- 見積り: 2日

**US-203 | P2 | Phase 2**
佐藤さんとして、**今日のエネルギーレベルと記録に応じた、私に向けた励ましがほしい**。テンプレの言葉は自分に向けられていない気がするからだ。
- 受け入れ条件:
  - Bedrock 連携でエネルギーレベル・記録内容を反映したメッセージを生成
  - 生成失敗時はテンプレートにフォールバック
  - 医療的アドバイスを含まないようプロンプトで制約し、レビューでガードレールを検証
  - 1ユーザーあたりの生成回数上限(コスト制御)
- 見積り: 3〜5日(プロンプト設計・安全性検証込み)

**US-204 | P2 | Phase 2**
田中さんとして、**「遠距離でもやれていること」を認めてほしい**。直接介護していない罪悪感があるからだ。
- 受け入れ条件:
  - 電話・手配・調整系のタスク(「電話で話した」「手続きをした」等)がタスクリストに追加される
  - 遠距離介護向けの意味づけ文言がある
- 見積り: 0.5日(タスクデータ追加のみ)

#### EPIC-3: 続けられる

**US-301 | P1 | Phase 1**
佐藤さんとして、**ホーム画面から1タップでアプリを開きたい**。ブラウザで URL を探すのは続かないからだ。
- 受け入れ条件:
  - PWA として「ホーム画面に追加」できる(manifest + service worker)
  - オフラインでも記録できる(静的エクスポート + localStorage なので技術的に相性が良い)
  - `basePath: /carequest` 配下で manifest / SW が正しく動く
- 見積り: 2〜3日(Next.js 16 静的エクスポートでの SW 検証込み)

**US-302 | P2 | Phase 2**
佐藤さんとして、**「今日は無理」の日に休むことを許可されたい**。開けなかった日が続くとアプリごと嫌になるからだ。
- 受け入れ条件:
  - 休息モード(実装済みの `restMode` を UI として完成させる)
  - 連続記録(ストリーク)を採用しない。途切れを責める通知を送らない
- 見積り: 1〜2日

**US-303 | P3 | Phase 2**
佐藤さんとして、**1日1回だけ、優しいリマインドがほしい**(オプトイン)。忘れて途切れるのは避けたいからだ。
- 受け入れ条件:
  - PWA プッシュ or メールで1日1回まで。デフォルトはオフ
  - 文言は「記録して」ではなく「今日もおつかれさまです」系
- 見積り: 3〜4日(プッシュ基盤の新設が必要)

#### EPIC-4: つながる

**US-401 | P2 | Phase 2**
佐藤さんとして、**同じように頑張っている人がいると感じたい**。孤独が一番つらいからだ。
- 受け入れ条件:
  - 「みんな」画面が実データ(本日の匿名集計)で動く
  - 個人が特定される情報・ランキング・順位は一切表示しない
  - 参加者が少ない日でも寂しく見えない表示(閾値未満は集計を出さない等)
- 見積り: 3日(集計 Lambda + DynamoDB 集計設計)

**US-402 | P2 | Phase 2〜3**
田中さんとして、**妹と「今週それぞれが父にしたこと」を共有したい**。分担の偏りと連絡漏れをなくしたいからだ。
- 受け入れ条件:
  - 家族グループの作成・招待(Cognito ベース)
  - 共有されるのは記録サマリーのみ。ふりかえりメモ(内心)は共有しない — これは重要な信頼要件
- 見積り: 5〜8日(認可設計含む。Phase 2 の中では最大の機能)

**US-403 | P3 | Phase 3**
山本さん(ケアマネ)として、**担当家族に「自分を労わるツール」として紹介したい**。
- 受け入れ条件:
  - 紹介用 LP・印刷チラシ(QR 付き)
  - 事業者向けの説明ページ(データの扱い・料金)
- 見積り: 2〜3日(開発というよりコンテンツ制作)

#### EPIC-5: 守られている

**US-501 | P0 | Phase 0**
佐藤さんとして、**私の記録が安全に扱われると確信したい**。介護記録は家族のプライバシーの塊だからだ。
- 受け入れ条件:
  - Cognito / DynamoDB の RemovalPolicy が本番安全(既存 P2 Issue)
  - CORS が本番オリジンに限定される
  - プライバシーポリシーページ(何を保存し、何をしないか)

## 5. 開発費用見積もり

### 5.1 前提

- 通貨: 日本円(税抜)
- 人日単価の想定: フリーランス中堅 5〜8万円/人日、開発会社 8〜12万円/人日
- 現在の MVP は完成済みのため、**見積もり対象は Phase 0〜2 の追加開発**
- 工数は上記ユーザーストーリーの見積りを積み上げ、管理・テスト・予備で 30% を上乗せ

### 5.2 工数積み上げ

### 5.3 体制別の費用シナリオ

| シナリオ | 内訳 | 概算費用 |
| --- | --- | --- |
| **A. 本人 + AI エージェント(現体制)** | Claude Code(Max プラン等)月額 1〜3万円 × 6ヶ月 + 本人の時間。AI 支援で実質工数は 1/2〜1/3 に圧縮可能 | **6〜20万円**(自分の人件費を除く) |
| **B. フリーランスに外注** | 42人日 × 5〜8万円 | **210〜340万円** |
| **C. 開発会社に発注** | 42人日 × 8〜12万円 + ディレクション費 15〜20% | **390〜590万円** |

**推奨はシナリオ A**。本プロジェクトはコードベースが小さく、CI・スモークテスト・ドキュメント(AGENTS.md、project-skills.md)が AI エージェント前提で整備済みのため、AI 協働開発の効率が最大化される構成になっています。外注する場合も、Phase 2 の US-402(家族共有)のような認可設計を含む部分のみのスポット発注が費用対効果に優れます。

### 5.5 費用に関する意思決定ポイント

1. **Bedrock 導入(US-203)はランニングコストが跳ねる唯一の機能**。導入前に AWS Budgets でアラームを設定し、生成回数上限をコードで強制すること
2. **Phase 2 着手はデータで判断**。Phase 1 の継続率が悪いのに Phase 2 に投資しない(42人日のうち約半分は Phase 2)
3. 助成金(自治体の介護テック支援・ヘルスケア系スタートアップ支援)は営利化前でも申請可能なものがあり、シナリオ B/C を選ぶ場合の原資になりうる
