## この文書の目的

T10(サインイン時のローカル→AWS 同期、US-103)は「ローカルファースト方針の人間決定待ち」でブロックされています。ブロックの実態は **決定に必要な材料が揃っていないこと** です。本書はその材料を提供し、人間オーナーが Yes/No を判断できる状態にすることを目的とします。

対応リスク: **R-02(localStorage 消失によるユーザーデータ喪失)の恒久軽減**。現在 MVP は localStorage が唯一の保存先で、端末変更・ブラウザデータ削除でデータが失われ得ます。AWS 同期はこの穴を塞ぐ Phase 1 の最重要機能です。

前提となる他タスク: **T27(Lambda の sk を `log.id` ベースに変更 = 冪等な PUT)**。本設計はこの変更を土台にします。T27 未完了の状態では Phase B(自動同期)は着手できません(理由は後述)。

## 1. ローカルファースト原則(この設計の憲法)

トーンガイド(`.claude/skills/carequest-product-tone/SKILL.md`)と設計原則(`docs/design-principles.md`)の「ローカルファースト」を、同期設計における具体的な規範に落とし込みます。

1. **localStorage が常に真(source of truth)。AWS はバックアップ。**
   - 記録の作成・編集・削除は、まず localStorage に書く。これが唯一の「確定」の瞬間。
   - AWS への送信はあくまで「バックアップの複製」であり、失敗しても記録が失われることはない。
2. **オフラインでも全機能が動く。**
   - サインインなし・ネットワークなしでも、記録・ふりかえり・ポイント・履歴・相談窓口導線のすべてが完結する。同期は enhancement であり、blocker にしない(トーンガイド「AWS 同期は enhancement であり blocker にしない」)。
3. **サーバーはローカルを上書きしない。**
   - サーバー → ローカル方向の取り込みは「まだ手元にない記録を足す」だけ。手元の記録を消す・書き換えることはしない(`lib/import.ts` のマージ方針と同一思想)。
4. **同期はユーザーに主導権がある。**
   - 少なくとも Phase A では、同期(バックアップ)は明示的なボタンで起きる。勝手に大量通信しない。サインイン誘導も控えめに(トーンガイド「押し付けない」)。
5. **10秒ルールを侵さない。**
   - 記録完了の体験に同期を割り込ませない。同期は記録完了後の背景処理か、別画面のボタンで行い、確認ダイアログで記録を止めない。

> この原則に反する実装は、たとえ「整合性のため」でも採用しない。分散データの整合性より「手元の記録が絶対に消えない・止まらない」を優先する。

## 2. 同期プロトコル

### 2.1 データモデルと冪等キー

- フロントの記録は `CareLog`(`lib/types.ts`)。フィールド: `id, taskId, title, points, completedAt, date, energyLevel`。
- サーバー(DynamoDB): `pk = userId`、`sk = log.id`(T27 で変更)。これにより **同じ記録を何度送っても 1 行にしかならない**(冪等な PUT)。
- **`log.id` を同期の冪等キーとする。** これは `lib/import.ts` が既に採用しているキーと同一(`existing.logs.map((log) => log.id)` で重複排除)。ローカルとサーバーで同じキーを使うことで、マージ方針を両方向で一貫させる。

### 2.2 何を・いつ・どの方向に送るか

| 方向 | 何を | いつ(Phase A) | いつ(Phase B) |
|---|---|---|---|
| ローカル → サーバー(バックアップ) | ローカルの全 `logs` を冪等 PUT(サーバーに無い id、または内容が異なる id) | 「バックアップ」ボタン押下時 | サインイン成功時 + 記録追加後(デバウンス) |
| サーバー → ローカル(復元) | サーバーにあってローカルに無い `logs` | 「復元」ボタン押下時 | サインイン成功時(初回のみ / 端末追加時) |

- **差分 PUT の判定**: ローカルの各 log について、サーバー側の同 id が「無い」または「内容が異なる」ものだけを送る。冪等 PUT なので、判定を誤って全件送っても重複行は生まれない(安全側に倒せる)。実装の初期は「全件 PUT」でも正しく動く。差分最適化は後から入れられる(段階導入しやすい)。
- **方向の非対称性**: この同期は「バックアップと復元」であって双方向リアルタイム同期ではない。削除の伝播は Phase A/B のスコープ外(後述のエッジケース参照)。

### 2.3 今回の同期範囲(スコープ)

- **同期するもの**: `logs`(介護記録)、および将来的に `customTasks`。R-02 の主対象は「失われると痛い介護記録」なので、まず `logs` を最優先。
- **同期しないもの(この端末に留める)**: `note`(ふりかえりメモ = 内心)、`user`(プロフィール・設定)、`energyHistory`、`supportNudgeLastShown`、`onboardingShown`。
  - `note` を同期しない理由は **設計原則「内心は共有しない」** と整合。ただし本人のバックアップとしては将来同期する余地がある(決定シート D-4 参照)。現状のバックエンド(`/entries`)は logs 前提なので、まず logs に限定する。
- `lib/import.ts` は logs 以外(customTasks, note, goodThings, energyHistory)もマージ対象にしているが、それは「ユーザー自身が書き出した完全なバックアップファイル」を取り込む機能。AWS 同期は現行バックエンド構造(entries = logs)に合わせ、まず logs に絞る。両者は目的が異なるので範囲が違ってよい。

## 3. 競合解決

**`lib/import.ts` のマージ方針を全面的に踏襲する。** 新しい競合解決ロジックを発明しない(発明はバグの温床)。

### 3.1 踏襲する原則

- **既存優先(existing wins)**: マージの基準は既存側。`lib/import.ts` の `mergeStates` は `existing.logs` をそのまま残し、`imported` からは「まだ無い id」だけを後ろに足す。
  - サーバー → ローカル方向でも同じ: ローカルにある記録は残し、サーバーにしか無い記録だけをローカルに足す。**ローカルの記録がサーバーの内容で上書きされることはない。**
- **id で重複排除**: `log.id` の集合で判定。同じ id は 1 件に統合。
- **note は空のときだけ取り込む**: 今回 note は同期スコープ外だが、将来同期する場合もこの原則(黙って上書きしない)を守る。
- **goodThings は和集合**: 将来 user を同期する場合の原則。

### 3.2 サーバー → ローカル取り込みは必ず sanitize パイプラインを通す(★重要)

`lib/import.ts` は取り込み前に必ず `sanitizeRawState`(`lib/storage.ts`)を通しています(コメント「生 JSON を直接マージ・保存しない」)。

**AWS からフェッチしたデータも、生 JSON を信用せず、要素単位で sanitize してからマージする。**

- `fetchCareEntries`(`lib/api.ts`)は現状レスポンスを無検証で `CareLog[]` にキャストしている。これは「生 JSON を信用しない原則」の違反であり、**T31 で `sanitizeLog` 相当の要素単位検証を通すよう修正予定**。T10 はこの sanitize 済みの入口に乗る(T31 と T10 の依存を明記)。
- sanitize の効果: 壊れた要素・悪意ある要素(不正な points/date、pk 汚染の残骸など)を混入前に静かに除外する。`sanitizeLog` は `points`(有限数値)・`date`(YYYY-MM-DD)・`id`(文字列)を必須で厳格検証し、不正な log は捨てる(全捨てはしない)。
- **原則: ネットワーク越しに来たものは、ファイルインポートと同格に「信用しない入力」として扱う。**

### 3.3 「既存優先」の限界と割り切り

「既存優先」は **同じ id で内容が食い違う場合、ローカルの内容を勝たせる** ことを意味します。これは「手元の端末が真」というローカルファースト原則の帰結です。

- メリット: ローカルの編集が同期で巻き戻らない。実装が単純で、`lib/import.ts` と完全に一貫する。
- 割り切り: 「別端末での編集が、この端末に反映されない」場合がある(エッジケース E-1・E-4 参照)。MVP ではこれを許容する。真の双方向マージ(last-write-wins や CRDT)は Phase C 以降の検討事項(決定シート D-2)。

## 4. 失敗時の挙動

**大原則: 同期が失敗しても、記録はローカルに必ず残る。** 同期はバックアップであり、失敗は「バックアップが取れなかった」にすぎず「記録が消えた」ではない。

### 4.1 挙動

1. ローカル書き込みは同期より先に完了しているので、同期失敗はデータ喪失に直結しない。
2. 同期失敗を **赤い警告で出さない**(トーンガイド「エラーも穏やかに」「赤い警告ではなく落ち着いた表現でローカルに残っていることを伝える」)。
3. 失敗しても記録操作をブロックしない。10秒ルールを守る。
4. `saveCareState`(ローカル保存)自体の失敗は同期とは別問題。これは T31 で可視化予定(「記録を保存できませんでした。端末の空き容量をご確認ください」)。同期失敗とローカル保存失敗を混同しない。

### 4.2 文言(案 / トーンガイド準拠)

- 同期失敗: **「同期できませんでした。記録はこの端末にちゃんと残っています。」**
- リトライ案内(任意・控えめ): **「あとでもう一度お試しいただけます。」**(「今すぐやり直して」と急かさない)
- 成功時(控えめに): **「バックアップが完了しました。」** / 復元時「◯件の記録を読み込みました。」(`lib/import.ts` の既存文言と揃える)
- 差分なし: 「読み込みは完了しました。新しく増えた記録はありませんでした。」(`lib/import.ts` 既存文言を流用)

> 文言はいずれも「記録は無事」を最初に伝え、責めない・急かさない。確定文言は実装時に `.claude/skills/carequest-product-tone` で最終レビューする。

### 4.3 リトライ方針

- Phase A(手動): 失敗したら何もしない(ユーザーがまたボタンを押せる)。自動リトライで通信を増やさない(R-05 コスト・押し付けない原則)。
- Phase B(自動): 失敗は静かに握り、次のトリガー(次回サインイン・次回記録)で再送を試みる。指数バックオフ等の凝った仕組みは入れない(冪等 PUT なので単純再送で安全)。

## 5. 段階導入案

小さく出して、各段で価値を確定させる(ローカルファーストを崩さず、可逆的に進める)。

### Phase A: 手動バックアップ / 復元ボタン(★まずここまで)

- 設定画面などに「今の記録をバックアップする」「バックアップから復元する」ボタンを置く。
- サインイン済みのときだけ有効。未サインインなら「サインインするとバックアップできます」と控えめに案内(機能はブロックしない)。
- ローカル → サーバー(冪等 PUT 全件 or 差分)、サーバー → ローカル(sanitize + マージ)。
- **T27(冪等 sk)完了が前提**。ただし全件 PUT で動くので差分最適化は不要。
- 価値: R-02 の軽減を最短で提供。ユーザーが主導権を持つので「勝手に通信する」不安がない。JSON エクスポート(US-503)と役割が近いが、こちらはサインインで端末をまたげる。

### Phase B: サインイン時の自動同期

- サインイン成功をトリガーに、自動で「復元(サーバー→ローカル)」→「バックアップ(ローカル→サーバー)」を実行。
- 記録追加後もデバウンスして背景でバックアップ(10秒ルールを侵さないよう記録完了の後)。
- 失敗は静かに握り、次トリガーで再送(4.3)。
- **T27 完了が必須**。自動再送で同じ記録が何度も送られるため、冪等 PUT でないと重複行が増殖する。
- 価値: ユーザーが意識せずバックアップされる。US-103 の本来の姿。

### Phase C 以降(スコープ外・将来検討)

- 削除の伝播、双方向マージの高度化、note/customTasks/user の同期、複数端末のリアルタイム反映。決定シート D-2・D-3・D-4 参照。

## 6. エッジケース

| ID | ケース | 挙動(この設計の方針) |
|---|---|---|
| E-1 | **同一 `log.id` で内容が異なる**(別端末で同じ記録を編集した等) | 「既存優先」でローカルを勝たせる(3.3)。サーバーの異なる内容はローカルに反映しない。冪等 PUT なのでローカル → サーバー方向では最新のローカル内容で上書きされる。MVP はこの割り切りを許容(D-2)。 |
| E-2 | **端末の時計ずれ** | `date`(YYYY-MM-DD)と `completedAt` はクライアント生成。時計がずれた端末では日付がずれ得る。**タイムスタンプを競合解決に使わない**(既存優先は id ベースで、時刻比較しない)ので、時計ずれが誤マージを起こさない設計。ただし記録の日付自体は端末時計依存という限界は残る(既存アプリの前提と同じ。本同期で悪化させない)。 |
| E-3 | **長期間オフライン後の大量差分** | ローカルに溜まった記録を、再オンライン時にまとめて冪等 PUT。全件 PUT でも重複は生じない。件数が多い場合は API スロットリング(T29: 10rps)に当たり得るため、**バッチ送信 + レート内チャンク**を実装時に考慮(1回の同期で数百件を一気に投げない)。Phase B では失敗分を次トリガーで再送するので、途中で切れても最終的に揃う。 |
| E-4 | **複数端末の同時書き込み** | 各端末が独立に localStorage に書き、それぞれサーバーへ冪等 PUT。id が異なる記録は和集合として全端末に揃う(id 重複排除)。同一 id の同時編集は E-1 の割り切り(最後に PUT した端末の内容がサーバーに残る = last-writer-wins だが、各端末のローカルは既存優先で自分の内容を保持)。真の整合はスコープ外(D-2)。 |
| E-5 | **サインアウト時の扱い** | サインアウトしても **ローカルの記録は消さない**(ローカルファースト)。サーバー上のデータはそのまま残る(次回サインインで復元可能)。サインアウトで localStorage をクリアする実装は **禁止**。 |
| E-6 | **アカウント削除時のデータの扱い** | アカウント削除 = サーバー上のバックアップ(DynamoDB の該当 `pk=userId` の行)を削除。**ローカルの記録は削除しない**(端末の記録は本人のもの)。削除操作は「サーバーのバックアップを消す。この端末の記録は残る」と明示する。プライバシーポリシー(`app/privacy/page.tsx`)・R-01 と整合させ、削除フローは実装時に人間レビュー必須。プライバシー面の要件があるため決定シート D-5 で扱う。 |
| E-7 | **未サインインでバックアップ操作** | 機能をブロックせず、控えめに「サインインするとバックアップできます」と案内(押し付けない原則)。 |
| E-8 | **記録の削除がサーバーに伝播しない** | Phase A/B は「追加のバックアップ」であり削除同期は非対応。ローカルで消した記録が、別端末での復元やサーバー PUT で復活し得る。MVP は許容し、削除伝播は Phase C(D-3)。 |
| E-9 | **sanitize で一部要素が落ちる**(サーバーの壊れた行) | `sanitizeLog` が不正要素だけを静かに除外し、健全な記録は取り込む(全捨てしない)。ユーザーには穏やかに(必要なら「一部の記録を整えて読み込みました」)。 |

## 7. 決定シート(人間オーナーの判断が必要な点)

各決定点に選択肢・おすすめ度(★★★=強く推奨 / ★★=推奨 / ★=非推奨または将来）・一言の理由を添えます。
**D-1 だけでも「これで進めて」と承認されれば、T10 の Phase A が着手可能** になります(D-2〜D-5 は Phase A の実装をブロックしません)。

### D-1. そもそもローカルファースト方針で進めるか(T10 着手の可否)

| 選択肢 | おすすめ | 一言の理由 |
|---|---|---|
| **A. ローカルファースト(localStorage が真、AWS はバックアップ)で進める** | ★★★ | トーンガイド・design-principles と一貫。オフライン全機能・10秒ルールを守れる。R-02 を可逆的に軽減。human-todo.md の既定推奨も local-first。 |
| B. AWS ファースト(サーバーが真、ローカルはキャッシュ) | ★ | サインイン必須化に近づき「サインインなしで完結」を壊す。オフライン体験が劣化。本アプリの思想に反する。 |

> **この D-1 が承認されれば T10 のブロックが外れます。** Issue「Decide local-first vs AWS-first saving」にコメントで記録してください(human-todo.md 参照)。

### D-2. 同一 id で内容が食い違うときの競合解決

| 選択肢 | おすすめ | 一言の理由 |
|---|---|---|
| **A. 既存優先(ローカルを勝たせる。`lib/import.ts` 踏襲)** | ★★★ | 既存マージと完全一貫・実装単純・ローカルの編集が巻き戻らない。MVP に十分。 |
| B. Last-write-wins(タイムスタンプで新しい方) | ★★ | 直感的だが時計ずれ(E-2)に弱く、比較用の信頼できる更新時刻が今ない。 |
| C. 双方向マージ / CRDT | ★ | 過剰。分散整合の複雑さを MVP に持ち込むとバグと工数が跳ねる。Phase C で必要になったら。 |

### D-3. 削除の同期(伝播)を今回入れるか

| 選択肢 | おすすめ | 一言の理由 |
|---|---|---|
| **A. 入れない(Phase A/B は追加バックアップのみ)** | ★★★ | 「データを壊さない」を最優先。削除伝播は復活バグ・誤削除の伝播リスクがあり、MVP では追加だけで R-02 を十分軽減できる。 |
| B. 論理削除(tombstone)で伝播する | ★★ | 正しくやるなら tombstone だが、スキーマ拡張と全端末の合意が要る。Phase C 相当。 |

### D-4. note(ふりかえりメモ)・user・customTasks を同期範囲に含めるか

| 選択肢 | おすすめ | 一言の理由 |
|---|---|---|
| **A. まず logs のみ(note は同期しない)** | ★★★ | 設計原則「内心は共有しない」と整合。現行バックエンドが entries=logs 前提。R-02 の主対象(失って痛い記録)を最短で守れる。 |
| B. logs + customTasks を同期 | ★★ | customTasks も失うと痛い。バックエンド拡張が要るので Phase B 以降で追加候補。 |
| C. note も本人バックアップとして同期(共有はしない) | ★ | 「共有しない」と「本人のバックアップ」は別だが、混同リスク・暗号化検討が要る。急がない。慎重に。 |

### D-5. アカウント削除時のサーバーデータの扱い(プライバシー)
