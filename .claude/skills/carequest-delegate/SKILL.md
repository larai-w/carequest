# Care Quest 委任ワークフロー(プランナー → ワーカー)

役割分担: **メインセッション(Fable 等の上位モデル)= プランナー**が戦略・タスク立案・レビュー・コミットを担い、**carequest-worker サブエージェント(Sonnet/Opus)= ワーカー**が実装する。この仕組みはすべてリポジトリ内(`.claude/agents/`, `.claude/skills/`, `docs/`)にあるため、どのユーザー・どのマシンでも同じように動く。

## プランナーの手順

0. **PM レンズ**: バッチ立案時は `docs/project-management.md` の「ITIL / PMP の観点」のチェックリスト(価値・リスク・変更タイプ・品質・教訓)を通す。オーナー方針(2026-07-10)により必須
1. **立案**: `docs/strategy.md` のユーザーストーリーから次のタスクを選び、`docs/task-list.md` に受け入れ条件つきで記載する(GitHub Issue があれば番号を対応づける)
2. **委任**: Agent ツールで `subagent_type: "carequest-worker"` を spawn する。エージェント定義はセッション開始時に読み込まれるため、`carequest-worker` が未登録の場合は `general-purpose` + `model` 指定で代替し、`.claude/agents/carequest-worker.md` の本文ルールをプロンプトに含める。プロンプトには次を必ず含める:
   - タスク1件の内容と受け入れ条件(コピーして渡す。参照だけにしない)
   - 対象ファイルのヒント(わかる範囲で)
   - 「コミットしない」ことの念押し
3. **モデル選択**(spawn 時の `model` パラメータ):

   | タスクの性質 | model |
   | --- | --- |
   | UI追加・文言・データ追加・小さめのリファクタ | `sonnet`(既定) |
   | 認証/同期/Service Worker/インフラ設計など難所 | `opus` |
   | 戦略・タスク立案・レビュー・リリース判断 | プランナー自身(委任しない) |

4. **レビュー**: ワーカーの報告を受けたら差分を確認し、lint/build を自分でも再実行。必要なら /code-review を使う。トーン(carequest-product-tone)逸脱は必ず直す
5. **確定**: `docs/task-list.md` のチェックを更新 → コミット(Co-Authored-By を付与)→ 人間の作業が発生したら `docs/human-todo.md` に追記
6. **並列化**: 依存のないタスクは複数ワーカーを並列で spawn してよい。同じファイルを触るタスクは直列にする

## ワーカーに委任しないもの

- `main` へのマージ、本番デプロイ、AWS への書き込み(人間の承認事項)
- プロダクト判断(ローカルファースト方針の変更など)
- `docs/strategy.md` の改訂

## 人間(リポジトリオーナー)の関与ポイント

`docs/human-todo.md` に集約する。典型: GitHub 認証・Secrets・実メールテスト・`cdk deploy`・development→main のリリース判断。

## バッチ完了時のふりかえり手順

バッチの全タスクがコミット済みになったら、プランナーは以下の3ステップを実施する。

### ステップ1: 教訓の抽出

- 各タスクの実行結果メモ(task-list.md)を振り返り、次の観点で教訓を拾い出す:
  - ワーカーの報告と実際の結果が食い違った箇所(例: lint green 報告 → 実際は違反あり)
  - プランナーが引き取る必要があった作業(セッション上限・ワーカーの見落とし)
  - 受け入れ条件に書いていなかったが問題になったエッジケース
  - 次バッチへの繰越課題や「ワーカー提案」の要否判断

### ステップ2: 繰り返し失敗はスキルまたはワーカープロンプトテンプレへ必ず反映

- **同じ失敗が2回以上出たら、スキルまたはワーカープロンプトの共通テンプレ(下記セクション)を直すことを義務とする**
- 更新対象の例:
  - ワーカーが lint を再実行せずに報告する → テンプレの「最終レポート形式」に「lint を直前に再実行した結果を貼る」を追記
  - セッション上限中断が起きやすいタスク → 受け入れ条件に「中断時の引き継ぎメモを残す」を追加するガイドを記入
  - 特定のパターン(hydration/schema migration 等)で誤実装が出た → carequest-dev スキルまたはこのスキルの注意点に追記
- 口頭・記憶のみの「教訓化」は認めない。必ずファイルに書く

### ステップ3: improvement-log.md に記録

- `docs/improvement-log.md` に新しいバッチのセクションを追加(フォーマットはファイル内の「追記ガイド」参照)
- 反映先の識別子(スキルファイルパス・テンプレ名・DoD 項目名)を明記する
- この記録自体が次バッチの立案インプットになる(バッチ立案チェックリストを参照)

## ワーカープロンプトの共通テンプレ

プランナーがワーカーを spawn するときに毎回手書きしている定型部を雛形化したもの。タスク固有の内容(受け入れ条件・対象ファイル等)を差し込んで使う。

> **このテンプレ自体が改善対象です。** 失敗パターンが出たらステップ2の手順に従ってテンプレを修正し、改善履歴を improvement-log.md に残してください。

---

```
あなたは Care Quest の実装ワーカーです。プランナーが立案したタスクを1件だけ、受け入れ条件どおりに実装します。
作業ディレクトリ: /Users/irevail8/Documents/veai_ecosystem/carequest

# 作業開始前に必ず読むもの
1. AGENTS.md(Next.js のバージョン固有ルール。node_modules/next/dist/docs/ の該当ガイドを先に読む)
2. .claude/skills/carequest-dev/SKILL.md(静的エクスポートの落とし穴・必須チェック)
3. .claude/skills/carequest-product-tone/SKILL.md(文言・トーン。ユーザー向け文言を書くなら必読)
4. docs/task-list.md の「T◯◯」セクション(受け入れ条件の全文を確認)

# ルール(厳守)
- **コミット・プッシュ・デプロイはしない**(プランナーがレビュー後に行う)
- 委任された1タスクのスコープのみ変更する。スコープ外の改善はレポートに「提案」として書くに留める
- 変更許可領域: [ここにタスク固有のファイル・ディレクトリを列挙]
  ※並行ワーカーとの競合防止のため、許可領域外のファイルは変更しない
- AWS への書き込み系操作はしない。infra 変更は synth まで

# 並行実行時の検証コマンド制限
- **npm run build・npm run test:e2e(E2E)はプランナーが統合後に実行**するため、ワーカーは実行しない
- ワーカーが実行してよいのは: npm run lint / npm test(ユニットテストのみ) / cd infra && npm run synth
- ただし並行実行でない(単独実行)タスクの場合は、npm run build まで実行してよい

# タスク内容
[ここにタスクのタイトル・背景・受け入れ条件をコピーして貼る]

# 最終レポート形式(日本語で出力)
以下をすべて含めること:
1. 変更ファイル一覧(パスと変更概要)
2. 受け入れ条件ごとの充足状況(条件文 → ○/△/× と根拠)
3. 検証コマンドと結果(lint を最終編集後に再実行した出力を必ず貼る)
4. 残課題・人間の確認が必要な点
```

---

### テンプレ使用上の注意

- `変更許可領域` は並行ワーカーが同じファイルを踏まないよう、タスクごとに明示する
- `並行実行時の検証コマンド制限` は、並行実行の場合のみ「npm run build は実行しない」を適用する。単独実行なら build まで実行させる
- lint は **最終編集後に再実行**させることを明示する(eslint キャッシュで古い結果が出た事例あり: improvement-log 第7バッチ参照)
- 長大なタスク(目安: 受け入れ条件が8件超 or CDK+フロント同時変更)はセッション上限による中断リスクを受け入れ条件に追記する
